## User Request

### Requested result
Make Yente reliably show the Discord typing indicator while a user request is active, including quiet thinking and tool work, and stop when the request ends.

### Explicit constraints
- Keep the solution simple and use the existing periodic Discord typing refresh.
- Complete the-usual workflow through implementation and verification.
- Do not deploy or mutate production without explicit authorization.

### Accepted tradeoffs and residuals
- Existing requests already in progress when the change takes effect do not require retroactive typing support.

**Goal:** Keep Discord typing refreshed while the runner is working on a Discord-origin user request, including quiet thinking and tools, and stop refreshing when that work ends.

**Architecture:** The runner publishes its current selected Discord destinations at work boundaries. The host uses that activity with the existing immediate typing call and four-second refresh. For ordinary Discord messages, the existing inbound row stores the same normalized address used by typing; no new source columns are needed. The host preserves the existing bounded cold-start grace, followed by activity-based refresh. An idle warm container does not itself imply work.

**Tech Stack:** TypeScript, Node.js, Bun, SQLite, Vitest, Bun test, existing Discord adapter.

## Global constraints and decisions

- Work in `/home/dan/code/nanoclaw-yente-typing/.worktrees/yente-discord-typing` and follow its `AGENTS.md` and `docs/build-and-runtime.md`. Do not deploy, mutate production, or call live Discord without explicit authorization.
- Preserve the immediate typing hint and existing bounded 15-second grace during cold wake; a failed wake or cancellation should stop it as soon as its outcome is known. Beyond that grace, only selected active Discord-origin user work keeps refreshing. Queued, delayed, parked, accumulated, held, scheduled-task-only, and context-only work must not keep a periodic indicator running.
- A resolved result or terminal failure ends matching selected work; stop refresh for the cancelled request at `/stop` acknowledgement without changing provider cleanup. Intermediate delivery must not stop an active request. `send_message` can be either interim or final, and the host cannot reliably distinguish these at delivery; keep refreshing while the provider still reports active work and cease future ticks once its result is observed. A final message delivered before the provider result can therefore briefly be followed by another typing call. Discord controls client-side expiry: stopping calls does not immediately erase the displayed indicator.
- Retain non-Discord typing behavior and the host's existing four-second refresh. Do not change the host liveness heartbeat, GWS correlation behavior, recovery safety, or introduce a recovery scheduler or general IPC framework. Do not infer actual execution from pending/processing/recovery acknowledgements or a recovery record alone.
- Actual Discord adapter ingress does not set `replyTo`, so its stored delivery tuple is also its source. Only the operator CLI can set a reply override; it can synthesize a Discord-targeted event while sending the answer elsewhere. Discord bridge rows use `kind='chat-sdk'`, while the CLI's synthetic events use `kind='chat'`; verify eligibility from real stored rows so an operator request redirected to another Discord destination is not mistaken for Discord ingress. Do not add source schema or recovery-record machinery solely to preserve extended typing for that operator-only case. Preserve its existing routing and one-shot hint; never guess a missing source destination.

## Activity transport

Use the existing outbound session DB and delivery poll as the first candidate: the container already writes `session_state` in `outbound.db`, and the host opens that DB for running sessions about once a second. An ephemeral current-activity value, overwritten on changes and periodically while work is active, can be read during that existing poll before its early return for no messages, with no new schema or separately opened DB on each four-second typing tick. The runner should publish only selected user-work destinations and an empty set when none is active. Bound the age of a value so a failed final write cannot cause endless typing, and allow a later successful update to correct a failed write; diagnose repeated publication failures. The host must reject a value from a prior container instance; assess the existing launch lease as a generation identifier without exposing its secret or changing GWS behavior. Stale activity after an abrupt stop must not resurrect on replacement; use existing verified container-stop cleanup. Keep calls to storage bounded and do not let activity reporting break provider work.

This DB approach is a candidate, not yet behaviorally proven: check its actual read/write, contention, startup/lease and shutdown behavior locally. If it cannot safely provide current activity, investigate the existing stdout stream as a small alternative, with bounded framing, actual cross-runtime tests, current-container ownership, and stream failure handling. Do not declare success based on an untested carrier. Update `docs/build-and-runtime.md`, `CLAUDE.md`, and any other statements of host/container communication only where the chosen implementation makes them inaccurate.
